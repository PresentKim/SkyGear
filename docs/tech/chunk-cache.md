# 클라이언트 청크 캐시 (blob cache)

배드락 클라이언트는 서버가 보낸 서브청크·바이옴 데이터를 xxhash64 값으로 저장해 두는 **blob 캐시**가 있다.
캐시는 접속이 끝나도 남아 있어서, 다시 접속하거나 같은 청크를 다시 받을 때 바뀌지 않은 데이터는 해시만 받으면 된다.
Dragonfly(`third_party/dragonfly/server/session/chunk.go`)는 이 방식을 이미 구현해 두었고, 클라이언트가 캐시를 켜고 접속하면 그대로 쓴다.

## 패킷 흐름

| 순서 | 패킷 | 방향 | 내용 |
|---|---|---|---|
| 1 | `ClientCacheStatus{Enabled}` | 클라이언트 → 서버 | 접속할 때 한 번 보낸다. 캐시를 지원하는지 알린다(닌텐도 스위치 등은 `false`). gophertunnel 의 `Conn.ClientCacheEnabled()` 가 이 값이다 |
| 2 | `LevelChunk{CacheEnabled: true, BlobHashes}` | 서버 → 클라이언트 | 서브청크 요청 모드에서는 바이옴 blob 해시 하나만 보낸다(`SubChunkCount 0`, `SubChunkLimit`) |
| 3 | `SubChunkRequest` | 클라이언트 → 서버 | 서브청크를 요청한다 |
| 4 | `SubChunk{CacheEnabled: true}` | 서버 → 클라이언트 | 각 항목의 `BlobHash` 에 블록 데이터 해시를, `RawPayload` 에는 블록 엔티티 NBT 만 담는다. 공기뿐인 서브청크는 `SuccessAllAir` 로 보낸다 |
| 5 | `ClientCacheBlobStatus{HitHashes, MissHashes}` | 클라이언트 → 서버 | 이미 있는 해시(hit)와 없는 해시(miss) |
| 6 | `ClientCacheMissResponse{Blobs}` | 서버 → 클라이언트 | miss 의 실제 데이터. 서버는 보낸 blob 을 hit·miss 응답이 올 때까지 세션에 들고 있다(최대 4096개) |

## 캐시 키와 blob 내용 (구현 스펙)

**키는 blob 내용의 xxhash64(시드 0) 하나뿐이다.** 청크 x·z 좌표, 월드, 차원, 서버는 키에 들어가지 않는다.
`ClientCacheBlobStatus`·`ClientCacheMissResponse` 에는 해시와 내용만 있고 좌표가 없어서, 클라이언트는 해시로만 blob 을 찾을 수 있다.
Mojang 설명(Tomcc)에 따르면 캐시는 접속이 끝나도 남고, 내용이 정확히 같으면 다른 서버에서 받은 blob 도 다시 쓴다.
클라이언트는 받은 blob 의 해시를 직접 계산해 맞지 않으면 버린다. `ClientCacheBlobStatus` 하나에는 해시가 4095 개까지 들어간다.

따라서 **다른 좌표의 청크도 같은 blob 이면 전송이 줄어든다.** 다만 "같은 blob" 의 조건이 좁다. Dragonfly 가 만드는 blob 은 다음과 같다.

| blob | 단위 | 바이트에 들어가는 것 | 다른 좌표에서 같아지는 조건 |
|---|---|---|---|
| 서브청크 | 16×16×16 한 칸 | 버전(9), 층 수, **서브청크 Y 번호**, 층마다 비트 폭·인덱스·팔레트(블록 **런타임 ID**) | 같은 Y 칸이고, 블록 배치·팔레트 순서·층 수가 모두 같음 |
| 바이옴 | 칼럼 전체(모든 높이) | 바이옴 팔레트 저장소 | 칼럼의 바이옴이 모두 같음 |

- **Y 는 키에 들어간다**: 서브청크 앞부분에 Y 번호 바이트가 있어서, 같은 블록이라도 한 칸 위·아래면 다른 blob 이다(아래 시험의 (4,0)).
- **x·z 는 들어가지 않는다**: 같은 Y 칸의 같은 블록이면 다른 청크라도 같은 blob 이다((3,0), (5,0)).
- **팔레트 순서가 같아야 한다**: 팔레트는 블록이 처음 놓인 순서로 쌓인다. 저장할 때 `Compact` 가 안 쓰는 항목만 빼고 순서는 그대로 둔다. 그래서 같은 모양이라도 놓은 순서가 다르면 다른 blob 이 된다. 반대로 지운 블록이 남긴 빈 항목은 저장·로드 뒤 사라진다((5,0): 다이아몬드로 채운 뒤 돌로 덮은 칸 = 처음부터 돌인 칸). 아직 저장 전인 칼럼은 빈 항목을 들고 있어서 다를 수 있다.
- **공기뿐인 서브청크는 blob 이 없다**(`SuccessAllAir`). 하늘섬 맵은 대부분 이 경우여서 보낼 것이 거의 없다.
- **블록 엔티티 NBT 는 blob 밖이다**: `RawPayload` 로 매번 보낸다.
- **런타임 ID 를 쓴다**: Mojang 설명은 blob 에 디스크 형식(블록 NBT 팔레트)을 쓰라고 하지만, Dragonfly 는 네트워크 형식(런타임 ID)을 쓴다. 해시가 런타임 ID 를 포함하므로 커스텀 블록 목록이 바뀌어 ID 가 밀리면 해시도 바뀐다. 예전 blob 이 잘못 쓰이지는 않지만, 그 업데이트 뒤 첫 접속은 모두 miss 가 된다.

### 활용 방향

- 같은 템플릿에서 시작한 섬, 복사한 세이브, 재접속, 같은 세이브의 재방문은 이미 hit 이 된다.
- 다른 좌표 간 재사용을 늘리려면 blob 을 만들기 전에 팔레트를 정규화(예: 런타임 ID 순으로 정렬)하면 된다. 그러면 놓은 순서가 달라도 같은 모양이면 같은 blob 이 된다. Y 번호는 형식에 들어가 있어 뺄 수 없다.
- 커스텀 블록을 추가할 때 기존 런타임 ID 가 밀리지 않게 하면 업데이트 뒤에도 캐시가 유지된다.

## 시험 도구 (`test/chunk-caching` 브랜치)

### `/cachetest` (운영자)

| 명령 | 하는 일 |
|---|---|
| `/cachetest target <세이브 번호>` | 시험할 세이브를 정한다(`data/saves/<번호>`) |
| `/cachetest start` | 로비에서 실행. 그 세이브의 월드를 `data/cachetest/<계정>` 으로 복사해 읽기 전용으로 열고(틱 없음), 관전 모드로 옮긴다. 열린(활성) 세이브는 복사하지 않는다 |
| `/cachetest resend` | 시험 월드에서 로드된 청크를 모두 다시 보낸다 |
| `/cachetest stop` | 로비로 돌아가고 복사본을 지운다(나가기만 해도 지운다) |
| `/cachetest status` | 대상, 클라이언트 캐시 여부, 이번 접속의 hit/miss 누적 |

시험 중 청크를 보낼 때마다 채팅에 한 줄씩 나온다(공기뿐인 청크는 합계에만). 서버 로그에도 `cache test chunk` 로 모두 남는다.

```
청크 (3, 0) blob 2: 새로 1, 캐시 1 (같은 좌표 0, 다른 좌표 1, 이전 접속 0) 공기 23, 패킷 안 1 B
합계 청크 861 (공기뿐 852), blob 874: 새로 12, 캐시 862 (같은 좌표 0, 다른 좌표 861, 이전 접속 1), 응답 없음 0
```

- **새로**: 클라이언트가 miss 로 답해 지금 데이터를 보낸 blob. **캐시**: hit 으로 답해 해시만 보낸 blob.
- 캐시는 그 해시를 이 접속에서 전에 어디로 보냈는지로 나눈다. **같은 좌표**: 이 청크로 보낸 적 있음. **다른 좌표**: 다른 청크로만 보낸 적 있음(좌표가 달라도 재사용된 것). **이전 접속**: 이 접속에선 처음인데 이미 있음(디스크 캐시).
- **응답 없음**: 10초 안에 hit/miss 를 답하지 않은 해시. **캐시 없이**: 캐시를 쓰지 않고 블록 데이터를 패킷에 담아 보낸 서브청크.
- 보고는 청크의 해시가 모두 답을 받고 1.5초 동안 새 패킷이 없을 때 나온다(`common/sghook/chunkwatch.go`).

시험용 세이브는 `go run ./tools/cachetestsave data` 로 만들 수 있다(서버를 끈 채로).

### 그 밖의 도구

- `common/sghook/chunkcache.go`: 연결마다 캐시 패킷 수를 센다. `sghook.ChunkCache(p)`, `ResetChunkCache(p)`, `ResendChunks(p, tx)`(로드된 청크를 모두 다시 보냄), `ChunkCacheLog`(blob 상태·miss 응답 INFO 로그).
- `/sgdebug chunkcache <stats|reset|resend|log>`: 운영자용 명령. 실제 클라이언트로 `reset` → `resend` → `stats` 순서로 쓰면 다시 보낸 청크가 모두 hit 인지 본다.
- `tools/cachebot`: 캐시를 켠 가짜 클라이언트. blob 을 파일에 저장해 두어 재접속을 흉내 낸다. 서버의 `AuthEnabled = false`, 봇 이름을 `Admin.Operators` 에 넣고 쓴다.

```sh
go run ./tools/cachebot -resend -wait 10s   # 첫 접속 + 재전송
go run ./tools/cachebot -wait 10s           # 재접속 (cachebot.blobs 유지)
```

`tools/cachetestsave` 세이브로 `/cachetest` 를 돌린 결과(cachebot, 해시만으로 찾는 캐시):

| 청크 | 내용 | 첫 접속 | 재전송 | 재접속 |
|---|---|---|---|---|
| (2,0) | 돌 서브청크 4 | 새로 1 | 같은 좌표 | 이전 접속 |
| (3,0) | (2,0) 과 같은 돌, 다른 x | 새로 1 (주석) | 같은 좌표 | **다른 좌표** |
| (4,0) | 같은 돌, 서브청크 5 | 새로 1 | 같은 좌표 | 이전 접속 |
| (5,0) | 다이아몬드를 채운 뒤 돌로 덮음 | **다른 좌표** | 같은 좌표 | 다른 좌표 |
| (6,0) | 돌 + 흙 한 칸 | 새로 1 | 같은 좌표 | 이전 접속 |

(바이옴 blob 은 모든 청크가 같아서 늘 hit 이다.)
주석: (3,0) 은 (2,0) 의 데이터가 오기 전에 같은 해시를 받아 miss 로 답했다. 서버는 그 해시의 데이터를 한 번만 보낸다(miss 12 건에 응답 blob 11 개). 첫 miss 에서 세션의 blob 을 지우기 때문이다. 같은 내용이 늦게 온 (5,0) 은 처음부터 다른 좌표 hit 이었다. cachebot 은 해시만으로 찾으므로, 이 표는 **서버가 만드는 blob 바이트가 어디서 같아지는지**를 보여 준다. 실제 클라이언트도 해시로만 찾는지는 게임으로 `/cachetest` 를 돌려 확인한다.

로비(서브청크 대부분이 공기)에서 잰 결과:

| 경우 | LevelChunk | blob 서브청크 | hit | miss | miss 응답 |
|---|---|---|---|---|---|
| 첫 접속(빈 캐시) | 861 | 8 | 829 | 40 | 10 blob, 9030 B |
| 같은 접속에서 재전송 | 861 | 8 | 869 | 0 | 0 |
| 재접속(캐시 유지) | 861 | 8 | 868 | 1 | 1 blob, 1040 B |

miss 40 건에 blob 이 10 개인 것은 같은 바이옴 해시가 여러 청크에서 겹치기 때문이다(서버는 해시마다 한 번만 보낸다).

### 알게 된 점

- 클라이언트가 한 배치에 패킷을 너무 많이 보내면 gophertunnel 이 연결을 닫는다(`maximumInBatch`). 처음 만든 봇은 재전송 받은 861 청크의 `SubChunkRequest` 를 한 번에 보내서 로그 없이 끊겼다. 그래서 봇은 틱마다 64 개씩만 보낸다.
- Dragonfly 세션은 이런 읽기 오류로 끊길 때 로그를 남기지 않는다(`handlePackets` 가 그냥 끝난다).
