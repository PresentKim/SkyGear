## 3-5 Feature tests leave the root package

Goal: a feature's tests live in its package and run without the root package, where that is possible and gains something.

What decides whether a test can move at all. The features are installed by the root's `init` (`core.Install(Features...)`), once per process. A test binary of a feature package does not link the root, so nothing is installed in it: the hooks have no subscribers, the settings are not registered, `look.Hidden` and the followers are empty, the panel adapters of `farm` and `machine` are missing, the function variables a higher layer fills (`core.ShowMenu`, `core.UpdateBoard`) are nil, the recipes and the creative list of `catalog` do not exist, and after 3-4 a kind of another owner has no behaviour. Three consequences follow. A test that calls the feature's functions directly needs none of this and can move as it is. A test that drives the player handler or the session's lifecycle (15 files call `s.Handler(p)`, 12 `s.Join`, 5 `s.Fast`, 3 `s.Second`) reaches the feature only through its subscribers, so its binary must set the feature up, and every feature whose step runs before it in the chain and changes the outcome (the guards of `expand` and `island`, `autofill`, `copier` before `wand`); what such a test proves in a package is less than what it proves in the root, where the whole order is installed. And a test cannot be in package X if it imports a package that imports X: the tests of `machine` that use `farm`, `storage` or `conduit` (`machine_test.go` imports all three) must be in the external package `machine_test`, or stay above.

Setting features up in a package. `core.Install` panics on a second call and runs the features' `Check`; `machine`'s check fails unless `storage`, `farm`, `dimension` and `netstore` are set up too, and `machine`'s own tests cannot import them from inside the package. So a package test does not call `Install`. It calls the `Setup` of the features it needs, once, before the first event (a hook refuses a subscriber after its first `Emit`), which is what the two test files changed by 3-4 do. The support package should own that: `Setup(fs ...*core.Feature)` running each `Setup` once per binary and registering the settings.

The helpers. `testSession` is used by 67 of the 93 files, `loadAround` 63, `spawnPlayer` 49, `withPlayer` 49, `tick` 33, `machinePos` 26, `placeTestMachine` 23. `testSession` returns the root's `*session` over a `*Game` with a database; nothing a feature test uses of it is the root's but the embedded `core.Lifecycle` and `Handler`. A package `content/skygear/core/coretest` can give the same over `*core.Session`: a session on a synchronous world, registered so that `core.At` finds it (the panel providers depend on that), with the world handler, a player, a transaction, ticks, the lifecycle and a `core.PlayerHandler`; it finalises the block registry in its `init` as `helpers_test.go` does. `placeTestMachine` and `machinePos` need `machine` and belong in a second small package beside it (`machine/machinetest`). The root's helpers then become thin wrappers, so the tests that stay do not change.

What must stay in the root, about 36 files: the ten `pin_*_test.go` with their goldens and `pin_test.go`'s harness, `kinds_test.go`, `layers_test.go`, `helpers_test.go`, the benchmarks (`bench_test.go`, `pin_bench_test.go`, `netgraph_bench_test.go`, `rest_perf_test.go`), `handler_dispatch_test.go`, `bridge_effects_test.go`, `pack_test.go`, `persist_test.go`, `vanilla_persist_test.go`, `vanilla_test.go`, `migrate_retired_test.go`, `creative_test.go`, `commands_test.go`, `decor_test.go`, `names_test.go`, `admingive_test.go`, `blockcounts_test.go`, the two `debug_*_test.go`, `counterhooks_test.go`, `quickbar_test.go`, `windowtext_test.go`, `look_test.go`, `look_branches_test.go`. They test the wiring, the composed game, the pack or the saves, or they need every item registered in the game's order (runtime ids, the pack's names, the creative list). The eleven files that import `catalog`, `codex` or `screens` (`achievements`, `logrecipes`, `research`, `timed`, `barkfiber`, `codex`, `sieve`, `research_split`, `researchtext`, `screens`, `sidebar`) test content lists and screens over all features; those packages are no feature, and `screens`' tests need the whole list installed, so they stay as well.

What can move, about 48 files, by the highest feature a file imports: `farm` 12 (barrel, composter, crook, cropinfo, crops, harvester, lab, machine, magic, minetool, sapling, witchwater), `machine` 7 (animate, autoequip, fairyspell, magicsieve, monitor, naturegen, tier), `storage` 4, `fairy` 4, `tinker` 3, `handwork` 3, `progress` 3, `island` 3, `conduit` 2, `dimension` 2, `netstore` 2, `copier`, `elevator`, `wand` 1 each. The count is an upper bound: `machine_test.go`, `lab_test.go` and `minetool_test.go` land in `farm` only because they plant a crop or fill a barrel, and belong in `machine_test`; ten of the 48 drive the handler.

Recommendation: do not aim at "81 files". First `coretest` and `machinetest`, with the root's helpers as wrappers and no test moved (one task; the suite proves the helpers). Then move, one feature per task, only the files that test one feature through its own functions and pass when their package is run alone with at most that feature and its kind owners set up: the leaf features first (`elevator`, `handwork`, `copier`, `wand`, `fairy`, `tinker`), then `storage`, `farm`, `dimension`, `netstore`, `machine` last (as `machine_test`). A file that needs three or more features set up to pass stays in the root and is listed with the reason; that is where the composed game is tested. Expect 30 to 40 files to move and the root to keep 55 to 65. A task moves files and changes call sites, never an assertion; it reports `go test -list` of the root and of the package before and after (the same test names, none lost) and runs the moved package alone.

Risks: a test that passes in the root only because every feature is installed (found by running the package alone); a test that reaches an unexported root identifier (`s.g`, `s.state`, `savedState`, `giveItems`: 4, 4, 3 and 5 files, all in the stay list); item and block registration order differs between test binaries, so nothing that moves may assert a runtime id or a golden; one server join per process (`wire` and `dimension/popup_wire_test.go` stay alone); `Setup` twice in one binary panics on the repeated subscriber name, so the support package must remember what it set up.

Re-measure before planning: per root test file, the features whose `Setup` it needs to pass alone (try it), and the root identifiers it uses.
